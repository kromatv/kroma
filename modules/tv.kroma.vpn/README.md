# VPN

Managed WireGuard bridge (any provider) that torrent traffic routes through, with a live seal test.

The backend lives entirely in this module's own `server/` crate (`kroma-vpn`): the `ServerModule`, its admin routes, the `VpnProxyPort` the composition root registers, and the managed WireGuard->SOCKS5 bridge. It reaches the app only through the `HostCtx` seam. The Downloads module lists it under `optionalDependencies`: enable VPN first so the engine's SOCKS5 points at a live proxy.

Three ways in. **Mullvad** connects by itself: the module makes a WireGuard key with the host's random source, registers only the public half on the account (`api.mullvad.net`, purpose `vpn-provider`), and writes a config for the country or city the admin picks from Mullvad's public relay list. One device serves every relay, so changing place swaps the peer and calls the accounts API for nothing. The account number, device and key sit in `<data>/vpn/mullvad.json` (mode 0600) and never reach a browser. **Proton VPN** has no API for another app, so the page walks the admin through Proton's generator and takes the `.conf` it hands out, naming its server from the file's comments. **Any other provider** pastes its config. The facts behind both providers, with their sources, are in [`docs/reference/vpn-providers.md`](../../docs/reference/vpn-providers.md).

Kept configs can also go **in the router**. Each one checked on the page runs a bridge of its own on `vpnLocalPort` plus its slot (1 to 4), loopback only and behind the same SOCKS password. The manifest declares the five ports as one `net.listen` run (`"count": 5`), so the install screen says so and the host keeps every other module away from them. The `network` point offers each bridge as `vpn-<id>` beside the default `vpn`. A rule in Admin → Réseau then names it, so indexer searches can leave through one country and torrents through another. The name follows the file, never the default, so a pinned rule keeps its server when the card switches. A config that is the default's tunnel (the same key to the same peer) shares the default bridge, because two bridges on one key to one peer would steal each other's replies. Nothing runs in the router without a default tunnel, and taking a config out stops its bridge and deletes its copy of the key under `<data>/vpn/net/<id>`. A connected Mullvad device adds places the same way: "Ajouter ce lieu au routeur" keeps a config for another relay on the same key and address, never a relay the default or another place already reaches, and costs no device on the account. Its comment names the place (`# Mullvad se-sto-wg-001 · Sweden · Stockholm`), switching the default to it keeps the device, and leaving Mullvad drops every place built on the key. Proton counts each tunnel as one session (10 on VPN Plus); the page says so, because one past the limit opens and passes nothing.

The page's bandwidth band comes from the download module over the `tv.kroma.torrents/vpn` point, because `wireproxy` is userspace WireGuard: there is no `wg` interface here to read rx/tx off, and the engine's own transfer is the tunnel's throughput. The engine keeps the series and splits it by seal state, so a window where the bridge was down says so instead of drawing an unlabelled line.

Layout: `server/` (backend crate), `ui/` (frontend), `locales/` (i18n), `module.json` (manifest). See `modules/README.md` for the module authoring guide.
