# Messages

Every user-visible string is a key. The engine is `@kromatv/i18n` (TypeScript) and
`kroma-i18n` (Rust): the same flat `{ "key": "template" }` catalogs, the same
`{name}` interpolation, `$t(other.key)` quoting and CLDR plurals, so a
notification the server renders reads like the screen that shows it.

To translate KROMA or add a language, read [`translating.md`](translating.md).
This page is the developer's side.

## In short

| To | Run |
| --- | --- |
| See how far every language has come | `bun run i18n` |
| Add a message | `bun run i18n new player.skipIntro "Passer l'intro" en="Skip intro"` |
| Rename or delete one, everywhere | `bun run i18n rename <key> <new-key>`, `bun run i18n rm <key>` |
| Split a file that has grown too long | `bun run i18n mv admin.backup admin/backup` |
| Start a language | `bun run i18n add de` |
| Translate one | `/translate de` in Claude Code, or `bun run i18n translate de` |
| Say translations hold as they read | `bun run i18n confirm de player.` |
| Find what is wrong | `bun run i18n check` |

French is the source. Write a message there and in English, and nothing else
has to change: a language that lacks it reads its fallback. Types, locks and
file layout keep themselves in step under the dev server and on commit.
The rest of this page is how that works.

## One folder per language

```
packages/core/src/locales/
  i18n.json            the policy: source language, fallback, stages
  notes.json           what translators are told, by key or key prefix
  fr/                  the source language, complete by definition
    nav.json           one file per namespace
    admin.json
    admin/             or a folder, where a namespace is split
      backup.json
      sign-in.json
  en/
    nav.json
    admin/...          the same files as fr, kept that way by the tool
    i18n.lock          what each translation was made from
  messages.d.ts        the key types, generated and gitignored
```

A folder is a language and everything about it is inside. Nothing lists the
folders or the files. Adding a language is one command and removing one is
deleting its folder.

A namespace is the first segment of a key: `player.play` lives under `player`,
in `player.json` or in any file of a `player/` folder. Keys stay fully qualified
inside the file, so a grep for `player.play` lands on the line that defines it.

## Adding a message

```bash
bun run i18n new player.skipIntro "Passer l'intro" en="Skip intro"
```

That writes the message in `fr` and `en`, in the file of its namespace and in
key order, then updates the types and the locks. Where the namespace is split,
it lands beside the keys it looks most like, and `--file admin/backup` says
otherwise. Use it right away:

```ts
t('player.skipIntro')
```

`en` is `stable`, so the check asks for the text there too. No other language
has to change: a language that lacks a message reads it in its fallback, and the
report counts it as missing.

Editing the JSON by hand works as well. The dev server brings the types and the
locks in line each time a catalog is saved, and the pre-commit hook does the
same for a commit made without one running, so `bun run i18n sync` is rarely
typed.

Three more commands keep the catalogs tidy:

```bash
bun run i18n rename player.skip player.skipIntro   # every language, and the code
bun run i18n rm player.oldHint                      # every language
bun run i18n unused                                 # messages no source file names
```

`rename` keeps each translation and whether it was outdated, and rewrites the
key where a `.ts`, `.tsx` or `.rs` file names it as a whole string. `unused`
reads the TypeScript and the Rust. It is a list to read, not a verdict: a key
that arrives in data shows there too.

## Keys and variables are typed

`messages.d.ts` declares every message of the source language with the
variables its templates name. A key that does not exist does not compile, and
neither does a call that forgets a variable or passes one the message never
reads:

```ts
t('content.seasonCount')                // error: count is missing
t('content.seasonCount', { count: 2 })  // ok, and count must be a number
t('nav.home', { count: 2 })             // error: nav.home takes nothing
```

A plural variant (`content.seasonCount_one`) is not a key. Its base is, and the
variable that selects the variant is typed as a number.

A key built from a template is checked too, against the messages it could
name:

```ts
t(`jobs.status.${status}`)   // ok while a message starts with jobs.status.
t(`jobs.statu.${status}`)    // error: no message fits
```

It needs no cast, and it accepts any variables, because which message it names
is decided at runtime. So does a key that is one of several, a variable of type
`MessageKey`. A key that arrives as a plain `string`, a name the server sent
for instance, is the one case that still needs `as MessageKey`: nothing about
it can be checked. Where a generic gets in the way, give the key the type
`MessageKey` first.

The Vite dev server rewrites the types when a source-language file is saved.
`bun run i18n types` does the same without one, and `bun run typecheck` and
`bun install` run it first.

## Splitting a namespace

A namespace that has grown too long becomes a folder of files. The file names
are free, the keys do not change, and neither does any call site:

```bash
bun run i18n mv admin.backup admin/backup
```

That moves every message whose key starts with `admin.backup` into
`admin/backup.json`, in every language. Moving keys by hand in `fr` and running
`bun run i18n sync` does the same: every other language follows the files the
source keeps its keys in.

Splitting is also what loads less. A screen fetches the files whose keys it
names, so the backup page no longer downloads the sign-in settings.

## The policy file

`i18n.json` holds what a folder cannot say:

```json
{
  "source": "fr",
  "fallback": "en",
  "locales": {
    "en": { "stage": "stable" },
    "de": { "stage": "beta" }
  }
}
```

- `source` is the language the messages are written in. Its files are the
  complete set, they type the keys, and every fallback chain ends in it.
- `fallback` is what an unfinished translation reads in before the source.
- A locale's `stage` says how far it has come:

| Stage    | Offered to readers | Missing or outdated message |
| -------- | ------------------ | --------------------------- |
| `draft`  | no                 | reported                    |
| `beta`   | yes                | reported, reads in fallback |
| `stable` | yes                | fails the check             |

A folder the file does not name is a `draft`. It is typed, the dev tools can
render it, and nothing ships it: no picker lists it, no browser language selects
it, and the server does not embed it. Shipping a language is changing its stage,
which is a decision and not a percentage, so a language does not vanish from a
picker because someone added ten strings.

A locale can name another `fallback` of its own.

## Regional locales

A regional locale holds only what differs from its language. `fr-CH` is a
folder with a handful of messages, and everything else is read from `fr`. The
chain needs no configuration: `pt-BR` reads in `pt`, then `en`, then `fr`.

- A message `pt-BR` does not write and `pt` has is **inherited**. The report
  counts it as covered, `todo` does not list it, and a `stable` regional locale
  is not held to it.
- A message neither has is missing in both, and reads in the fallback.
- A language never borrows from its own region: a message only `pt-BR` has is
  missing for a `pt` reader.
- A browser asking for `fr-CH` gets the `fr-CH` folder where there is one, and
  `fr` otherwise. One asking for `fr-BE` gets `fr`.
- Plurals follow the language.

## Content follows the same rule

Titles, synopses, episode names, section headings and AI-written text are
stored per language too, and the server reads them by the rule the interface
uses. `crate::i18n` in `kroma-engine` is the one place that knows it:

- **Content locales.** A language keeps its own content unless the language
  its tag belongs to is offered as well. With `fr`, `fr-CH`, `en`, `pt-BR` and
  `zh-Hant` offered, content exists in `fr`, `en`, `pt-BR` and `zh-Hant`, and a
  `fr-CH` reader gets the French. That is also the list TMDB is asked for and
  the list an AI prompt writes in, so a regional variant costs no extra
  request.
- **Reading.** A reader's locale becomes its content locale before the
  database is asked, then falls back to the project fallback and the source.
- **TMDB.** It takes a language with an optional country and knows no script,
  so `zh-Hant` is asked as `zh-TW` and `zh-Hans` as `zh-CN`. Every row is
  still keyed by the locale.
- **Tags as they arrive.** `fr-ch`, `PT_br` and `zh-TW` resolve to `fr-CH`,
  `pt-BR` and `zh-Hant`, as they do on the clients.

Each offered content language adds one TMDB request per title and per season,
and staging a new one marks the whole catalogue stale once.

## What a reader of an unfinished language sees

Their language wherever it has a translation, and the fallback chain for the
rest. A key is never shown.

- **Web and TV (Vite).** The plugin knows, per file, which languages answer
  every message. For one that does not, the engine fetches that language's file
  and its fallback's together, and `useT()` waits for both.
- **Native (Metro).** Everything is in the bundle and the lookup walks the
  chain.
- **The server.** `build.rs` embeds the offered languages. At startup the gaps
  of a `beta` language are filled from its chain, a plural message whole from
  one language so a count never picks a variant from one and a template from
  another.

`LOCALES` from `@kromatv/core` lists the offered languages with their stage, so
a picker can mark the `beta` ones.

## Tracking progress

```bash
bun run i18n              # every language: stage, translated, outdated, missing
bun run i18n status de    # one language, file by file, with the keys left
bun run i18n status --md  # the overview as a markdown table
bun run i18n status --json
```

It counts the app, every module that ships messages, and the website
(`apps/www/messages`, under the name `www`). A message is:

- **missing** when the language has no text for it,
- **inherited** when a regional locale takes it from its language,
- **outdated** when the source text changed after the translation was made and
  the translation did not,
- **translated** otherwise, of which **unreviewed** when a machine wrote it and
  nobody has read it yet.

`i18n.lock`, in each language's folder, is what tells outdated from current. It
records two short digests per message: the source it was translated from and the
translation itself. Editing the translation makes it current again. Where the
source moved in a way that changes nothing for a language, a fixed typo for
instance, say so:

```bash
bun run i18n confirm en player.
```

A machine translation carries a mark in the lock until someone edits it or
runs `bun run i18n confirm de`. Unreviewed is a reminder, not a gate: it ships
like any other translation.

The lock is committed and `bun run i18n sync` writes it. On a merge conflict in
one, take either side and run sync again.

## Translating with Claude

`/translate de` in Claude Code, or `bun run i18n translate de` unattended.
Both run on the subscription the `claude` command is signed in with, both hand
the model the French source, the English text and the notes from `notes.json`,
and both mark what they write as unreviewed. See
[`translating.md`](translating.md#translate-with-claude).

## The check

`bun run i18n check` runs as a test (`packages/i18n-tools/src/workspace.test.ts`),
so it gates CI. It refuses:

- a key in a file of another namespace, or in another file than the source
  keeps it in,
- a key the source language does not have (`bun run i18n prune` removes them),
- a `{placeholder}` the source never passes,
- a plural variant without its base key beside it,
- an empty translation,
- a `$t()` that quotes a missing message, or one from another file,
- a language that does not name itself under `lang.<code>`,
- a `stable` language with a missing or outdated message,
- a note in `notes.json` about a key or a prefix no message has,
- a lock the files have moved past.

## How a screen gets its messages

No shell loads the whole catalog up front, and on the web no catalog ships in
the entry.
What the locale set reads before anything renders is each language's name for
itself, one string per language, which the plugin reads off the folders.

The rest travels with the code. The Vite plugin scans every source module for
string literals that are keys, `'admin.title'` or `` `pipeline.t.${stage}` ``,
and appends an import of each catalog file they belong to. That import is a tiny
module handing the engine one loader per locale for the file. The moment the
chunk evaluates, the engine fetches the rendered locale's file, and only that
one: a French reader never downloads `en/admin.json`. `useT()` suspends, through
React's `use()`, until what is in flight for its locale has landed, so the
route's pending state shows a moment longer and no key is ever painted.

Two cases fall outside the scan, and both still work:

- **A key built at runtime** from a variable, or read from data. Its first miss
  fetches every file of its namespace in that locale through `lazy`, the
  non-eager glob, and the provider redraws when they land. The key shows for
  one paint.
- **Metro.** A native bundle is one file, so every language is in it and
  nothing is fetched. `require.context` names the files without evaluating
  them: the language names are read at boot, and the rest of a language is
  parsed the first time that language is rendered.

Under vitest the plugin runs eager, so a component test that renders admin copy
has its catalog synchronously and nothing suspends.

A `$t(...)` reference may only quote a key of its own file, because files
arrive one at a time. The check enforces it.

### What the first screen fetches

A catalog file follows the chunk that names its keys, so a file is fetched at
boot exactly when a module naming it is in the entry chunk. Two habits put one
there by accident:

- **A route file importing from a page module** for `validateSearch` or
  `loader`. The router keeps those options in the eager half of the route, the
  page module comes with them, and so does every catalog it names. Keep what a
  route's options need in a small module of its own (`network-tabs.ts` beside
  `network.tsx`).
- **A shared module that mixes labels with logic.** A module is in a chunk
  whole. When the entry uses `langBase` from a file that also builds
  `lang.<code>` keys, the 192 language names arrive at boot. Keep the functions
  that name keys in a module of their own (`lang-labels.ts` beside `lang.ts`,
  `subtitle-stage.ts` beside `subtitles.ts`).

Two things watch it:

```bash
KROMA_I18N_REPORT=usage.json bun run build:web
```

writes, for each build environment, what every chunk names of every catalog
file, and under `boot` what the entry and its static imports fetch: the files,
how many messages each holds, how many the boot code names, and `via`, the
chain of imports from the entry down to the module that names the file.

`kroma({ bootMessages: 500 })` in a shell's `vite.config.ts` is a limit on that
number. A client build past it fails and prints the same list, heaviest file
first. The web client sets it; the TV shells bundle to one file and do not.

A key written in a comment names nothing, and neither do the engine's own
sources. A string that happens to equal a key still does, so a wire name and a
message should not share a spelling. `rename` rewrites every literal equal to
the key for the same reason, and lists the files it touched: read the list.

## Modules

A module keeps its messages in `locales/` beside its `module.json`, written in
English. Its front end registers them as a scope, layered ahead of the core
catalogs for that module's pages only.

It may keep them in either of two layouts, and every tool reads both:

```
locales/               one file per language
  en.json
  fr.json
  fr.lock

locales/               one folder per language, as the app does
  en/
    nav.json           one file per namespace
    settings/          or a folder, where a namespace is split
      advanced.json
  fr/
    nav.json
    i18n.lock
  notes.json           what translators are told, optional
```

A `locales/` that holds a folder is read as folders, and one that holds only
files as one file per language. In the folder layout a key starts with the
namespace of its file, as in the app: `nav.title` lives in `nav.json`, or in
any file of a `nav/` folder. There is no `i18n.json`: a module ships every
language it has a file or a folder for.

To move a module from the first layout to the second, split `en.json` into
`en/<namespace>.json`, move every other `<code>.json` into `<code>/` under any
name and its `<code>.lock` to `<code>/i18n.lock`, then run `kroma i18n sync`:
each language follows the files English keeps its keys in, and what was
outdated stays outdated.

The bundle is the same either way. `kroma build` packs one
`locales/<code>.json` per language, the files of a folder merged in path
order, and never a lock or the notes. A server reads that format and no other,
so a module can change layout without waiting for a server release.

The same commands work for a module, in this repository and for one built on
the published SDK:

```bash
bunx kroma i18n                     # this module's languages
bunx kroma i18n new page.empty "Nothing here yet" fr="Rien pour l'instant"
bunx kroma i18n add de
bunx kroma i18n todo de --out de.todo.json
bunx kroma i18n check
```

`add` starts a language as an empty catalog: `locales/de.json`, or in the
folder layout the first file English has, `locales/de/nav.json`, since git
keeps no empty folder. `mv` and `note` need the folder layout.

A module's keys are typed too. `kroma dev`, `kroma check` and `kroma i18n types`
write `ui/src/messages.d.ts`, gitignored, and `useT()` from the SDK then checks
a key written out against the module's messages and the app's, with their
variables. A key only runtime can name, a `string` variable or a template like
`` `flag.${name}` ``, is taken as it comes.

In this repository `bun run i18n` covers the modules as well: it measures each
one against the app's languages and stages (`--set tv.kroma.vpn` picks one).
The lock is beside each file (`locales/fr.lock`), or inside each folder
(`locales/fr/i18n.lock`), and is never packed into the bundle. A new language
changes the bundle, so it comes with a version bump in `module.json`.

A module may write a plural without a base key, `videos_one` and
`videos_other` with no `videos`. The key a caller names is still `videos`.

## Dev tools

The in-app panel (`@kromatv/i18n-devtools`, dev server only) is the same system
seen from the running app.

- **Switch locale** for the tab, drafts included.
- **See what answered.** Highlight paints every string by where it came from:
  its own catalog, a fallback language, no catalog at all, a translation whose
  source has changed since (outdated), or one a machine wrote that nobody has
  read (unreviewed). Browsing a screen shows what on it needs a person.
- **Status.** The panel shows the coverage of the rendered locale and its
  missing, outdated and unreviewed counts, the numbers `bun run i18n status`
  prints.
- **Edit in place.** Point at a string and press `Ctrl+Alt+E`: the editor shows
  the key, the source text and one field per plural form. Saving writes the
  catalog file through the same code as `bun run i18n fill` and updates the
  lock. The new text appears in place, in every open tab, with no reload.
- **Confirm in place.** `Ctrl+Alt+C` on an outdated or unreviewed string says
  its translation holds as it reads, as `bun run i18n confirm` does.

The catalogs plugin does the rest under the dev server. A catalog saved by any
means, the panel, an editor or the CLI, regenerates the key types, brings every
lock in line and is pushed to the page as it now reads. One limit: a key
deleted from a catalog stays on the page until the next load.

All of it applies to the app's own engine. A site that translates through
another one gets the locale switch and the marks, and none of the writing.
